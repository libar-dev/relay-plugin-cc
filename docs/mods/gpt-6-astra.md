# Relay Mods plan, GPT-6 Astra

## 1. Verdict

Build a command-first Mod for relay, with a stable companion bridge and an optional terminal interface.
For this user, a terminal job board is a later feature: current T3 does not implement the Mod drawing protocol.
The immediate gains are deterministic status/report commands, reliable direct controls, and faster delivery through existing relay machinery.
Keep the relay agent, command hooks, worker leases, recovery, and durable message accounting authoritative.
Do not replace those mechanisms until a separately tested adapter proves equivalent behavior.

## 3. Feature catalogue and responsibility boundaries

Sizes are relative implementation estimates: S is one narrow PR; M is a few focused PRs; L changes delivery or workflow semantics and needs a separate compatibility effort. Proposed command names use hyphens because registered Mod names do not support the colon in existing `/relay:status` names. Keep the existing Markdown commands available.

### F1. Deterministic status and report commands, build first

User value: `/relay-status` and then `/relay-result <id>` show authoritative results without asking Claude to run Bash and reformat them. Include effective state, attempt, owed work, violations, and whether a result was handed back. Add repository and Workflow scope before machine-wide browsing.

APIs: `session.start`, `$.command.register`, `command.run`, `$.plugin.root`, `$.session.cwd`, `$.process.run`. Mark read commands immediate. Use command text in headless hosts and permit a pane link later.

Companion changes: a versioned, bounded read bridge described below, explicit backend names, typed busy errors, and report pagination or a report-size refusal. No worker changes. Works in terminal, Desktop and headless engines; T3 text rendering has strong static evidence and remains a release smoke test. Risks are silent JSON truncation, stale attempts, and confusing an old report with current completion. Size M overall, with status alone S. Dependency: the read contract.

### F2. Direct steer, queue, continue, resume and cancel, build after durable receipts

User value: a deliberate user action reaches the companion without a Haiku relay turn. Offer `/relay-send`, `/relay-continue`, `/relay-resume`, `/relay-cancel` and a request-status command. Explain whether the backend accepted an interjection or queued another turn. Kimi's `steer:false` must appear as queue-follow-up behavior.

APIs: command registration, `command.run`, `$.process.run`, `$.state` for pending presentation; later Button/Input callbacks. Companion/runtime changes: durable request IDs, payload binding, queryable receipts, action preconditions, and a fast accept/reconcile path. Both CLI and future pane controls call the same bridge. All three host kinds can execute it; T3 mid-turn availability needs its own routing check. Risks are duplicate continuation after timeout, cancellation of a newer attempt, and permissions differing from Bash. Size M. Depends on F1 and the action contract. Do not implement mutations by constructing a shell command from user text.

### F3. Event-assisted delivery, investigate early and promote only after parity

User value: messages can reach an existing relay job sooner than the roughly two-minute Bash wait cycle. This is the strongest non-UI improvement for T3 workflows.

APIs: observe `session.receive`, `session.append`, `tool.call`, `classic.SubagentStart`, and `classic.SubagentStop`; use `$.clock.after` to coalesce work and `$.process.run` for a bounded companion call. `T:11948` describes receive events without a durable message UUID; `T:11108` gives append events a pinned transcript UUID and agent ID. Prefer a post-`next` append signal as the candidate trigger. Exclude virtual queue rows until their relationship to delivery rows is proved.

Companion/runtime changes: expose an agent-bound "reconcile relay inbox" operation under `lib/harness/`. It must read the existing transcript and use `syncRelayMessages`, its lock, UUID ledger and message IDs. An append notification is a wake signal, not a second source of message contents. Retry boundedly if transcript publication lags the event. Initially record timing/correlation only and never deliver from the Mod.

Works in all engine hosts; does not need T3 to render anything. Risks include pre-approval observation, duplicate wake events, transcript lag, Workflow adoption, and blocking Claude's event chain. Size L. Depends on a read-only agent/job mapping and a separate accepted-event parity experiment. Keep polling/guards as fallback, including after missed events and process restarts.

### F4. Failure and uncollected-result diagnostics, build

User value: find a completed job whose latest attempt was never handed back, an exhausted recovery, owed work, and relay violations. Relay 2.2.0 already supplies much of the evidence.

APIs: read commands, event-triggered refresh, `$.clock`, `$.ui.log` on hosts that display it, and disposable `$.state`. Companion changes: explicit handback coverage plus pending-message counts and structured diagnostic codes. `handedBackAt:null` alone is insufficient for old jobs or jobs never owned by a relay. Reading a report must not mark it handed back.

Diagnostics work everywhere through F1. Passive notices work in terminal/Desktop; current T3 needs a host notice adapter. Optional `$.prompt.submit` may wake Claude for a narrowly selected failure, but that is a model turn and must be an explicit preference. `$.session.send` to an agent is likewise not a durable job receipt. Risks are duplicate alerts, cross-session noise, and claiming receipt from a UI view. Size M. Depends on F1; automatic wakeups depend on durable deduplication and stop/refusal handling.

### F5. Setup inspector and validated launch configuration, build the inspector first

User value: inspect backend/home/model/effort and distinguish credentials present from verified sign-in. Later, build a valid launch request without hand-editing a header.

APIs: `/relay-setup`, `$.process.run`; common Input/Select controls if a renderer exists. Companion changes: wrap existing `buildSetupPage`; expose full registry capabilities and their notes, not only today's reduced `can` projection. Add a pure validation operation before adding launch actions. Keep model/home discovery in Node.

The inspector works as text everywhere and as a form in terminal/Desktop. Setup may take tens of seconds and should run on request, not every board refresh. A configuration change does not prove a live turn succeeds. Launching direct jobs also does not automatically provide a Claude Agent/Workflow slot. Size S for the inspector, M for validation/forms, L if expanded into a launch workflow. Depends on F1; writes/launches depend on F2.

### F6. Compact job board and report inspector, build later

User value: see active jobs, owed work, stale reads, errors and report availability without repeated commands. Provide one compact indicator and an explicitly opened pane with a report inspector. Render from one cached projection.

APIs: `ui.render` at Pane and AbovePrompt, `$.ui.open`, `$.ui.panes`, `$.ui.resolve`, `$.state`, `$.clock`, `session.attach`, and `$.session.surfaces`. Use Box/Text/Button/Input/Select/Markdown rather than terminal-only Raster or Image.

Companion changes: F1's bounded queries and F2's actions; no UI-owned job state. Works in terminal and Desktop local Code. Current T3 gets the text commands, not the board. Refresh while visible, with a small single-flight interval; stop drawing-related polling when no renderer is attached. Risks are refresh storms across sessions, report size, narrow terminals, and stale selection targeting a different attempt. Size M. Depends on F1; controls depend on F2. This is optional, not the first milestone.

### F7. Workflow job grouping, build a limited projection

User value: inspect jobs from one Workflow run and identify missing handbacks. The existing `status --workflow <run>` already finds jobs across repositories.

APIs: F1 commands and optionally F6's pane. Companion changes: expose Workflow/agent identifiers and labels consistently; group existing jobs. Do not invent observer/fixer/judge stages or finding ownership from prose. Those need an explicit workflow record not present in the current job API. Text works everywhere, graphical grouping in terminal/Desktop. Risk: incomplete job lists being mistaken for complete Workflow state. Size S for grouping, L for a workflow controller. Depends on F1. Defer role/finding management.

### F8. Narrow model-callable read tools, optional

User value: Claude can read typed relay status/results without generating Bash syntax. APIs: `$.tool.register` and exact-name `tool.call` handlers invoking the read bridge. Runtime changes: none beyond F1. Works in all hosts loading the Mod. It still takes a model tool-use step and is not the same as a free user command. Risks are added tool context and duplicating existing commands. Size S. Add only if actual usage shows Bash construction remains a problem; do not expose every bridge operation as a tool.

## 4. Phased implementation plan

### Phase 1, one PR: read-only `/relay-status`

Add `modules:["./register.ts"]` alongside the existing hooks object, a tiny Mod module, and `companion.mjs bridge` with only `describe` and bounded `status` operations. Use the existing validated view functions, not direct file assembly. Expose repository scope and explicit job lookup first. Keep `/relay:status` as fallback. No background polling, pane, mutation, setup probe or hook migration in this PR.

Acceptance criteria:

- A command-only terminal and streaming SDK run produces the expected answer with zero model turns. A manual T3 command reaches its transcript in a fresh Claude thread used for release validation; record T3 and Claude versions. No reliance on dynamic slash completion or `ui_log`.
- Response schema/version and explicit backend are validated. Status output is bounded before it crosses the Mod process limit. Unknown versions and truncated output produce a visible error.
- A busy read produces a typed retryable error, not an empty board or failed job. Command usage errors cannot fall through to model execution.
- Removing or disabling only the relay Mod leaves its existing hooks and commands working, subject to the host's hook policy. Global `disableAllHooks` is explicitly outside that guarantee. Mod load/reload/exit creates no job and changes no job record.
- Existing affected checks pass; the generated 2.1.307 contract is captured as a compatibility fixture without bundling unrelated MCP declarations.

### Phase 2: useful read access and durable user actions

First add bounded result retrieval, setup inspection, Workflow grouping and handback diagnostics. Then implement the action ledger and add direct message/cancel commands. These are separate reviewable PRs within the phase.

Acceptance criteria:

- Existing result exit semantics and report identity survive the bridge. A failed/cancelled job is not presented as a successful task just because the bridge read succeeded.
- Duplicate requests converge on one receipt; a reused ID with changed payload is refused. A killed companion after acceptance is reconciled by ID without a second message.
- The same action is correct under concurrent callers, a job advancing attempts, a cancellation race, and a worker restart. The worker enforces relevant preconditions at the mutation boundary.
- Kimi queueing is labeled accurately; capability-based actions do not assume all tasks or review jobs accept messages. Unresolved actions remain unresolved until authoritative evidence arrives.
- T3 idle commands are checked live. Mid-turn controls are advertised only after validating T3's send-now/queue path independently from Claude's `immediate` flag.

### Phase 3: event observations, then a delivery accelerator

Record only job/agent/message identities and timing. Compare Mod append signals against existing transcript delivery on both ordinary Agent and Workflow paths. If they correlate correctly, enable coalesced calls into the existing reconciler for a small opt-in cohort. Guards remain enabled.

Acceptance criteria:

- Compare accepted, refused, held-for-approval and consumed messages; none may reach the backend earlier than the authorized existing path.
- Observe correlation across adoption, reload, compaction, clear/resume, interruption and T3 process restart. Identical text sent twice remains two messages because identity, not content hashing, determines delivery.
- Repeated events, missing events and a crash after receipt cause neither duplicate backend delivery nor lost owed work.
- Measure message-to-backend latency against the current two-minute polling path. Retain the feature only if it improves latency without slowing unrelated events.
- No new fail-closed behavior, no bypass of classic hooks, no replacement of handback verification.

### Phase 4: optional terminal/Desktop interface

Add F6 and only the limited Workflow projection of F7. Reuse the shipped commands and bridge. Configuration forms may follow once validation and receipts are stable.

Acceptance criteria:

- Test narrow/wide terminal and Desktop common elements. The same commands still work with no renderer.
- Closing or reloading the pane never ends a worker. Refresh has one request in flight, backs off on errors and stops when irrelevant.
- Selected job and attempt remain fixed through refresh. Stale data is visible, and stale actions are rejected by the bridge.
- Opening a report does not claim a relay handback or inject it into model context. Sending it to Claude is a separate deliberate operation.

A T3 notice/drawing adapter is a separate host contribution, not a relay feature we can deliver solely by adding a Mod. If the user wants persistent T3 UI first, prioritize that host work before Phase 4.

### Proposed read contract

Add `companion.mjs bridge`, backed by a new `cli/bridge.mjs`. It accepts one bounded JSON request on stdin and produces one bounded JSON response on stdout. Diagnostics go to stderr. Start with `describe` and `status`; add `result`, `setup`, `request.get` and mutations in later phases.

The envelope should contain `protocolVersion:1`, `requestId`, `operation`, `ok`, and exactly one of `data` or `error`. Errors include stable `code`, human `message`, `retryable`, and an optional retry delay. A valid envelope may describe a failed job or rejected action: transport success, operation success and job outcome must be separate fields. Define exit 0 as a delivered protocol envelope, including a structured operation error; reserve nonzero exit/no valid envelope for bridge transport failure. This convention applies only to `bridge`, not legacy commands.

Readers ignore unknown additive fields and reject unsupported major protocol versions. `describe` reports protocol versions, relay version, operations, output limits and capabilities. Pin the Mod to the installed generated contract; do not infer compatibility from a docs page's date.

For status, default to 20 rows and cap at 100, with a proposed serialized response cap of 512 KiB. Return explicit `backend` for every job, an opaque per-job revision, attempt identity, `sampledAt`, scope, and `nextCursor`/`hasMore`. Bound nested summaries and diagnostic arrays too, with explicit omission counts. A cursor uses deterministic creation-time/job-ID ordering and a first-page upper bound; it is not a promise of an atomic machine-wide snapshot. Scope defaults to the current repository. `--all` becomes a deliberate bounded scope, never an unrestricted bulk dump.

For Phase 1, fail the requested read with `BUSY` rather than silently hiding a busy job. If later listing uses partial results, return per-job read errors and an explicit incomplete flag. Preserve the validated view logic in [view.mjs:48](/Users/darkomijic/dev-libar/relay-plugin-cc/plugins/relay/scripts/lib/jobs/view.mjs:48), including version fencing and settled retries. It protects a coherent job view; it does not establish a transaction spanning every job and ledger file.

For results, return attempt identity, report identity/hash, total bytes and a bounded chunk. Subsequent chunks must retain that identity; if the underlying report changes, return `REPORT_CHANGED` and restart rather than splice two attempts. Preserve exact report text and UTF-8 boundaries. Initially refusing an oversized report with a clear location is acceptable; silently cutting its ending is not. `loadReport` at `lib/jobs/view.mjs:106` already handles archived reports and must stay the source of report selection.

For setup, retain backend discovery in [lib/setup/page.mjs:47](/Users/darkomijic/dev-libar/relay-plugin-cc/plugins/relay/scripts/lib/setup/page.mjs:47). Expose complete registry capabilities from `lib/backends/types.d.ts:43`, not just the reduced `can` object in `lib/backends/setup.mjs:118`. Include credential/sign-in evidence, supported modes, web-search options, priority-tier support and explanatory notes. A pure request-validation operation should call the same request rules as launch; it must not start a job.

### Proposed durable action contract

Every mutation requires a caller-supplied request ID, a job ID and explicit operation arguments. Bind that ID to a canonical payload hash, including operation, job, message and relevant preconditions. Repeating the same ID/payload returns or advances the existing receipt; repeating it with different payload is an error. Record origin/session information for audit without making a reconnect require a new request.

Persist the reservation before any inbox write or process signal. Place receipts under the owning job directory, with atomic writes and a per-job submission lock using the existing ownership primitives. Do not put authoritative receipts in `$.store`. Keep them queryable for the job's retention lifetime and return a clear expired/pruned result afterwards.

For message operations, allocate one durable message ID in the reservation, then reuse it across inbox, claimed and outcome checks. [messages.mjs:17](/Users/darkomijic/dev-libar/relay-plugin-cc/plugins/relay/scripts/lib/jobs/messages.mjs:17) already accepts an ID, and `:83` checks the message locations. That alone is not idempotency: concurrent check/post and recovery still need the reservation/lock protocol. Use the existing relay UUID ledger pattern at `lib/harness/relay.mjs:639` as a reference, not as an excuse to share unrelated transcript identities with user action IDs.

Return explicit states such as `accepted`, `applied`, `rejected` and `unresolved`, along with the message ID and authoritative outcome when known. Define `applied` as the worker's recorded action, such as queued/steered/cancelled, not completion of the resulting coding task. The Mod must never convert accepted into completed optimistically.

Check state and attempt preconditions at the operation's mutation boundary. A continuation or resume must not start a second attempt after a concurrent caller already advanced it. A cancel intended for attempt A must not kill attempt B after automatic recovery. Ordinary UI timestamps are insufficient; pass the intended attempt plus applicable state preconditions, and have the lease owner enforce them.

Cancellation needs dedicated work in [cli/cancel.mjs:135](/Users/darkomijic/dev-libar/relay-plugin-cc/plugins/relay/scripts/cli/cancel.mjs:135), `:158`, and `:168`: terminal no-op receipts, inbox requests and process-tree escalation must all belong to the same durable action and intended attempt. Recovery may continue that action under the existing lease/ownership rules; blindly rerunning today's cancel command is not the contract. If making the escalation recoverable is too large for the action PR, ship message controls first and leave direct Mod cancellation disabled until it is correct.

Use a short accept path and `request.get` to reconcile. Today's [delivery.mjs:85](/Users/darkomijic/dev-libar/relay-plugin-cc/plugins/relay/scripts/lib/worker/delivery.mjs:85) can wait 60 seconds for acknowledgement, whereas `$.process.run` defaults to 30 seconds. On timeout, report "outcome unknown; reconciling request …," then query the same ID. Retry submission only with that same ID, through the idempotent endpoint. A reconnect can list unresolved requests for the selected job. No exactly-once guarantee should exceed what the worker/backend can actually prove.

### Mod runtime constraints

Call Node with an argv array, for example `['node', pluginRoot + '/scripts/companion.mjs', 'bridge']`, and JSON stdin; never interpolate message text into a shell. Read the string property `$.plugin.root` and await `$.session.cwd()` explicitly. Pass any needed session/agent identity from supported APIs or validated event data; do not assume `CLAUDE_ENV_FILE` exports are applied to Mod process calls. The jobs home is on the machine hosting Claude and may differ between a local terminal and a remote T3 provider. Mod-started processes run outside Claude's Bash sandbox, so retain relay's explicit backend mode and request validation rather than assuming Bash permissions govern a button or registered command.

The Mod is not Node and cannot import the companion's npm/Node modules. Keep calls statically recognizable as `$.namespace.method` and event names/matchers literal. Same-file top-level helpers have different analyzer support from imported helpers or methods: validate the actual structure with `claude plugin validate`. Register commands so one collision cannot prevent unrelated initialization. These restrictions are in the [creation guide](https://code.claude.com/docs/en/plugins/mods/create).

The current declarations cap **stdout and stderr separately at 4 MiB**, with truncation flags (`T:3590`, `T:8229`). Check those flags before parsing. A timed-out `process.run` kills its child; a detached relay worker may already be running. `process.spawn` belongs to the Mod and its iterator, and is killed on unload/stream closure (`T:3610`). Neither API should own a relay job's lifetime.

The [limits](https://code.claude.com/docs/en/plugins/mods/reference#limits) also include a 10-second hook execution budget excluding `next` and most API waits, a 1-second `.catch` budget, a default 1.5-second aggregate session-end budget, 4 MiB per filesystem read/write, 4 MiB total store, and 4,096 recent session entries. Do not flush a durable delivery protocol in `session.end`. Do not wrap the whole 900-second Stop gate in a process call whose maximum is 10 minutes.

Use `$.state` for disposable selection, cached reads and pending presentation; it supports version-checked writes (`T:3470`). It survives reload but resets on clear/resume/branch. Use `classic.SessionStart` to rebuild after those transitions; compaction also emits that classic event without resetting state. Use `$.store` for small preferences only: its cross-session read/modify/write is not atomic. None of these replace the job's durable records.

## 6. Test strategy

### Mod contract tests

Use the official [Mod test kit](https://code.claude.com/docs/en/plugins/mods/test), importing `test`, `expect` and `mock` from `claude-code/testing`, and run `claude plugin test`. Stub process responses, state, store and clocks. Test terminal, Desktop and no-surface paths explicitly. A missing stub or failed handler can be skipped, so assert the expected API calls, returned text and state transitions; "did not throw" is not sufficient.

Cover registration and command collisions, invalid arguments, unknown protocol versions, additive fields, malformed JSON, stderr diagnostics, both truncation flags, busy reads, nonterminal/cancelled/no-report results, empty lists and oversized nested records. For actions, cover timeout before reservation, timeout after acceptance, duplicate ID, changed payload, stale attempt, rejected worker outcome and reconnect reconciliation. Prove no new message ID appears during a retry.

Use mock clocks to verify one refresh in flight, backoff, teardown and reset behavior. Use `ui.mount` for narrow/wide terminal and Desktop common elements; assert missing surfaces do not prevent command execution. Assert that routine refresh never calls `prompt.submit` or `session.send`. Test post-interruption refusals without starting an automatic retry loop: since 2.1.304, new-work APIs can refuse until the user supplies input. See [interruption behavior](https://code.claude.com/docs/en/plugins/mods/api#calls-and-background-work-after-the-user-interrupts-a-turn).

### Companion and relay regression tests

Add bridge contract tests with isolated temporary jobs homes and fake backends. Validate stdout framing, byte caps, page ordering, cursor behavior, report identity, typed errors and legacy output compatibility. Inject crashes between reservation, posting, claiming, outcome and receipt update. Exercise two callers with the same request, two different requests, and a worker advancing attempts during cancellation. These are the tests that justify reliable controls.

Extend the relevant existing suites rather than duplicating their fixtures: `tests/busy-view.test.mjs`, `backend-views.test.mjs`, `setup-page.test.mjs`, `commands.test.mjs`, `message-account.test.mjs`, `relay-delivery.test.mjs`, `ownership.test.mjs`, `recovery.test.mjs`, `report-archive.test.mjs` and `process.test.mjs`. Run the affected suites during development, then the repository's `npm test`, `npm run check`, and `npm run check-version` for the release candidate. Keep test jobs entirely outside the user's production jobs home. I did not run the relay test suite in this research pass and do not claim it passes; the brief prohibited starting relay jobs, and the work was source inspection plus the permitted read-only companion calls.

## 8. Open questions only the user can answer

1. Is useful command access in T3 enough for the first release, or is persistent T3 UI the actual requirement? My default is command access first. Persistent UI requires work in T3 as well as relay.
2. Should any failure notification wake Claude and incur a model turn? My default is no automatic wakeups; expose diagnostics on request and use passive notices where the host supports them.
3. Should repository scope remain the default, with explicit Workflow/machine scope, or should cross-repository work be the primary view? My default is repository scope, while Workflow scope follows its existing cross-repository semantics.
4. Should direct launch controls create standalone relay jobs, or must every launch participate in Claude Agent/Workflow ownership and handback? My default is to preserve the current agent-mediated launch path and ship direct controls only for existing jobs.

These preferences do not block Phase 1. Remaining questions about T3 command routing, event approval timing, older loader compatibility and Desktop behavior are engineering validation work, not questions the user needs to solve.
